# Riskfate: The Living Guild — технічний фундамент

**Статус:** рекомендації до погодження, без затвердженого рушія або готової реалізації.

## 1. Пріоритет проєкту

Першою перевірюваною цінністю гри є **автономна поведінка героїв** і наслідки рішень гравця про гільдію. Продуктивність, підтримуваність і контроль складності важливіші за деталізовану графіку.

Не починати з MMORPG-сервера, складного 3D, процедурного відкритого світу, нейромереж для NPC або повного економічного симулятора: потреби в них не доведені.

## 2. Модель симуляції — технічна рекомендація

- **Ігрова логіка незалежна від візуалізації.** Одні й ті самі стани героїв мають відображатися на карті, в панелі та в журналі без дублювання правил.
- **Час симуляції окремо від FPS.** Прийняття рішень, економічні операції та бої оновлюються за логічними подіями/кроками, а анімаційне відображення — за потреби.
- **Логіка станів (FSM) + пріоритетні правила** замість важкого загального AI: підготовка → подорож → бій → повернення → відпочинок/торгівля/завдання → новий вихід.
- За потреби розбивати стан міста і стан героя на окремі модулі; не будувати великої ієрархії класів «про запас».
- Для налагодження записувати рішення й підставу їх прийняття (наприклад, «HP нижче власного порогу», «закінчилися припаси»).

Частоти оновлень, числові пороги здоров'я та параметри AI — **відкриті**, їх визначати за прототипом і тестами.

## 3. Мінімальні сутності — орієнтир, не готова схема даних

- **Герой:** стабільний ID, поточний стан, локація/мета, HP/MP, характеристики, спорядження, інвентар, гроші, обрані правила поведінки.
- **Локація:** ID, доступність, можливі супротивники, здобич, умови переходу.
- **Монстр/бій:** ціль, HP, ефекти, дії, результат, винагороди.
- **Гільдія:** бюджет, список героїв, завдання, правила та надалі власність.
- **Міська будівля/магазин:** власник, асортимент/послуги, кошти, запаси, доступність.

На першому етапі дані можуть бути невеликими й локальними; не створювати окрему базу даних або сервер без вимог.

## 4. Порядок виконання дій героя — робочий приклад

1. Перевірити, чи живий/здатний діяти персонаж.
2. Обробити неминучі наслідки бою та поточні ефекти.
3. Якщо небезпека критична — лікування, захист або відхід, якщо дозволено правилами.
4. Якщо ресурсів недостатньо або завдання виконане — повернення.
5. Якщо в місті — відпочинок, покупка доступних припасів, здача завдань, підготовка.
6. Інакше — вибір придатної цілі та продовження пригоди.

Не виконувати несумісні дії одночасно. Вихід із кожного стану має бути визначений, зокрема коли грошей немає, вороги скінчилися, втеча неможлива або пункт призначення недоступний.

## 5. Економічна та інформаційна цілісність

- Розділяти гроші героя, гільдії та магазину; не допускати подвійного нарахування.
- Покупка = перевірка коштів/наявності → атомарне списання та передача предмета.
- Завдання й нагороду не можна здати/отримати двічі.
- Стан має зберігатися та відновлюватися; формат збережень потребує версії та перевірки цілісності.
- Балансування проводити на контрольованих сценаріях (голод товарів, банкрутство героя, повторні бої, масові повернення).

Це цільові вимоги, **не підтвердження реалізації**.

## 6. Візуалізація та продуктивність

Прості 2D-об'єкти/іконки та векторний адаптивний UI мають передавати: місце героя, поточний стан, початок/результат бою, HP/MP, покупки, повернення та виконання завдання.

Не вимагати складної покадрової анімації, фізики кожного NPC чи повного рендеру всіх локацій. Масштабування перевіряти з різною кількістю героїв; не оголошувати FPS або максимальну кількість NPC без вимірювань.

## 7. Технології — рішення відкрите

Варіанти для майбутнього порівняння:
- **Godot 2D / Control:** зручний для ігрових сцен, UI та експорту, але потребує налаштування проєкту/збірок.
- **Web (HTML/CSS/JS):** природний для майже повністю інтерфейсної гри та швидкого тестування в браузері; для Steam потрібне окреме пакування/інтеграція.

Не переносити автоматично Godot 4.7.2, серверну архітектуру, 3D-рендерер чи CI-конфігурації з Riskfate 3D Pro. Рушій, цільові платформи, збереження й метод доставки — **потрібно погодити** перед створенням коду.

## 8. Перевірка мінімального циклу

Потрібні автоматизовані тести для основних переходів станів, бою, витрат предметів, покупки, повернення та цілісності грошей/інвентарю. Перевірити крайові випадки: нуль HP, порожній магазин, брак грошей, відсутність монстрів, переповнення інвентарю, порожня черга завдань, повторне завантаження.

Критерій приймання — герой здатен **самостійно і зрозуміло** пройти повний цикл, а користувач бачить, що саме відбувалося. Тестовий успіх не замінює художнього та ігрового приймання власником.
